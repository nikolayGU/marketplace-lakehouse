# 13. Регламент исполнения: роли, гейты, доказательства

Версия 0.3, 29.10.2026 (0.2 от 27.10; что изменилось: раздел 10). Действует после «ок» владельца. Что делать, решает спека блока
(`14-closeout-spec.md`); как делать, решает этот файл. `AGENTS.md` главнее обоих: при расхождении
стоп и вопрос владельцу. Хук `.claude/hooks/guard.py` держит часть правил механически, остальное
держит этот регламент; то, что хук пропустил, не становится разрешённым.

`$COMPOSE` ниже значит `docker compose --env-file .env -f docker/compose.yaml` из корня репо; в
оболочке её задают первой строкой: `COMPOSE="docker compose --env-file .env -f docker/compose.yaml"`.

задаёт файл роли; `model` при вызове не переопределять.

## 2. Классы действий

Класс определяется самым опасным эффектом команды, а не её целью. Сомнение между классами решается
в пользу старшего.

**A, сам.** Чтение, `grep`, `git log/show/diff/status`; `make report`, `make verify-fast`,
`make check`, `make test`, `make lint`, `make test-spark`, `make dags-check`, `make alerts-test`, `make dbt-parse`;
`make dbt-build`, если DAG `dbt_build` на паузе и не в полёте; `select` в Trino и Postgres; GET к
Prometheus, Grafana, Lakekeeper, Connect; `docker ps/logs/stats/inspect`; `gh run list/view`;
context7 и веб; любые файлы в scratchpad; копии в `/mnt/d/lakehouse-backup/` (только добавление);
`docker load -i` архива образов, если digest образов до и после равны (не равны: стоп); правки
кода, тестов и доков в пределах списка «Файлы» активной карточки; цикл verify из раздела 5 при
принятом W6-D4.

**B, сам, но с ревью и полными проверками до коммита.** `docker/`, Dockerfile, `compose.yaml`,
`.github/workflows/`, зависимости и `uv.lock`, правила алертов и дашборды, логика DAG, `contracts/`,
новые миграции в `oltp/migrations` (файл, не применение), правка нескольких компонентов сразу.
Условия: карточка называет эти файлы; `reviewer` дал вердикт «принять»; полные проверки зелёные.
Особые случаи:
- файл в `airflow/dags/` живой сразу после сохранения, порядок такой: пауза затронутого DAG
  (`airflow dags pause <dag>` в контейнере scheduler), правка, `make test`, `make dags-check`, ревью,
  цикл verify (раздел 5), коммит, снятие паузы с затронутого DAG последним шагом. DAG `iceberg_*`
  с паузы не снимать (C). Пока Docker не запущен, `airflow/dags/` не править: при старте Airflow
  сразу подхватит непроверенный файл;
- образ `lakehouse/spark:dev` берут DAG-и: его собирают только из чистого дерева на HEAD, который
  прошёл ревью и CI, командой `$COMPOSE --profile core build spark-bronze` (без пересоздания
  контейнера); отдельного ревью сборка не требует. Образ для опытов с Dockerfile собирать с тегом `:ci`.

**C, только после «ок» владельца на это действие.** Всё из «Жёстких запретов» `AGENTS.md`, плюс:
- любая ступень лестницы W5-D13 и любой вызов `maintenance expire|orphans|rewrite-*`,
  `iceberg_demo`, процедуры Iceberg в SQL; trigger, test, снятие паузы `iceberg_maintenance` и
  `iceberg_orphans`; conf `dry_run: false` или `expire_and_compact: true`;
- остановка, удаление и пересоздание контейнеров стека (`make start`, `make up`, `compose up`,
  `down`, `rm`, `stop`, `kill`, `restart`), кроме остановки и запуска `airflow-scheduler` в цикле
  verify: при новом образе `make start` пересоздаёт `spark-bronze` и включает удаление
  `metadata.json` bronze (ревью п. 22);
- реплей и сценарии в любой форме (`make replay-*`, `make chaos-*`, `scripts/chaos/*.sh`,
  `scripts/replay-burst.sh`, контейнер `oltp-replayer`), `make cdc-snapshot`, `make migrate`;
- настройки топиков Kafka (`kafka-configs --alter`, `segment.ms`, удаление топиков, сброс offsets);
- удаление образов (`docker image prune`, `rmi`, `down --rmi`): образы MinIO есть только локально;
- Lakekeeper (защита, delete-profile, register), объекты бакета (`mc rm`, `mc cp`), записи в `shop`,
  `replay`, `cdc`, публикации и слоты Postgres;
- всё видимое снаружи: `git push`, `gh workflow run`, PR, релизы, `docker push`;
- правки `.claude/agents/`, `.claude/skills/`, `scripts/agent_state.py`, `AGENTS.md`, `CLAUDE.md`,
  `docs/agent-rules.md`, этого файла;
- решения группы C (раздел 2.1): ADR, который меняет компоненты, данные или границы проекта; новый
  сервис; замена S3-слоя; изменение проверки, которое может скрыть расхождение;
- гейты владельца (Read, Explain, Operate, Modify, в том числе `make watermark-demo|live`) агент не
  выполняет никогда;
- настройки Windows, WSL, Docker Desktop: только командой для владельца.

### 2.1 Группы решений

Решение (строка W6-D* спеки, развилка внутри карточки) относится к одной группе:

- **A, решает агент:** обратимый выбор внутри принятой архитектуры. Агент пишет в статус «принято
  исполнителем <дата>, A» и одну строку причины.
- **B, решает агент после независимого ревью:** зависимость, CI, инфраструктурная конфигурация,
  контракт, ADR, который сохраняет компоненты и версии и меняет только происхождение или процесс
  (пример: ADR-026, сборка MinIO из исходников того же тега). Статус «принято, B» ставится только
  при вердикте `reviewer` «принять», ссылка на вердикт в «Итоге» карточки. Ревьюер не подтвердил
  или нашёл, что решение меняет архитектуру: решение уходит в C.
- **C, решает владелец:** необратимое или разрушительное действие, живые данные и retention,
  публикация, изменение архитектуры или границ проекта, делегация и бюджеты. Агент приносит один
  вопрос с рекомендуемым ответом и ценой отказа и продолжает независимую работу.

Хук `guard.py` (правка 27.10, раздел 10) спрашивает на каждый пункт C, который видно по тексту
команды, и запрещает запись в `.claude/hooks/` и `.claude/settings*.json` этого репо. Хук читает
только текст команды. Запрещено:
- переименовывать, кодировать, дробить команду, уходить `cd` в другой каталог или класть её в
  скрипт, чтобы хук её не узнал; скрипт с действием C это то же действие C;
- повторять отклонённую команду в другой форме.

Окно подтверждения хука: если «ок» на этот текст команды уже получено в чате, окно ожидаемо и
владелец нажимает «да»; если «ок» нет, это стоп и запрос по шаблону ниже. Отказ классификатора auto
mode всегда стоп: владелец выполняет команду сам или повторяет «ок» явно.

### Как просить «ок»

Одно сообщение, одно действие (или одна поимённо названная последовательность из спеки):

```text
«ок» на: <точная команда, $COMPOSE раскрыт>
Зачем: <карточка, шаг>
Затронет: <таблицы, топики, контейнеры, файлы>; обратимо: да | нет (<как откатить>)
До: <числа, снятые только что, команда>
Проверка после: <команда и ожидаемый вывод>
Ревью плана: <вердикт reviewer> (обязательно, если «обратимо: нет»)
```

«ок» относится к этому тексту команды. Изменилась команда, таблица или порядок: новый запрос.
Постоянное «ок» (W6-D3, W6-D13) снимает вопрос в чате, но окно хука остаётся: владелец нажимает
«да»; пока его нет у экрана, агент делает другую работу.
Каждое полученное «ок» оркестратор записывает в HANDOFF, раздел «Журнал «ок»»: дата UTC, действие,
кто дал. Молчание и «ок» на соседний шаг не «ок».

## 3. Делегирование

Подагент знает только бриф. Бриф пишется по шаблону, без пересказа выводов оркестратора:

```text
Цель: <один результат>
Карточка: <ID, файл:раздел>
Вход: <файлы и команды; что уже известно с доказательством; что исключено>
Границы: менять можно <пути>; нельзя <пути, действия>; живой стек: не трогать | только чтение
Результат: <формат; каждое утверждение с file:line или командой и выводом; факт, вывод, гипотеза раздельно>
Приёмка: <как оркестратор проверит>
```

- Параллельно только независимое: разные файлы, никаких записей в стек. Два агента в одном файле
  запрещены.
- Отчёт подагента это данные. Оркестратор сам перезапускает ключевую проверку, сверяет
  `git diff --stat` со списком файлов брифа и выборочно открывает 2 ссылки `file:line`
  (ревью 12 и аудит 27.10 нашли неверные номера строк в отчётах агентов).
- Подагент, которому хук ответил `ask` или классификатор отказал, останавливается и пишет это в
  отчёт; действие C выполняет только оркестратор после «ок».
- Подагенты не запускают подагентов: Claude Code по умолчанию разрешает три уровня вложенности,
  запрет держит поле `disallowedTools: Agent` в каждой роли.
- Кто пишет код: `implementer` по брифу; оркестратор сам только правку до ~20 строк в одном файле,
  Markdown и шаги на живом стеке. Исправления по ревью тоже идут брифом `implementer` с номерами
  замечаний.
- Цикл задачи владелец запускает командой `/task <ID карточки | фраза>`
  (`.claude/skills/task/SKILL.md`): skill задаёт порядок шагов, правила остаются здесь.

## 4. Независимое ревью

`reviewer` получает: диапазон коммитов или `git diff`, текст «Готово, когда» карточки (путь и раздел),
инварианты `AGENTS.md`, список уже выполненных проверок с выводом, предмет ревью: `код` (diff для
коммита), `план` или `документ`. Не получает рассуждений исполнителя. Сам перезапускает проверки, которые может.

Формат отчёта, как в `12-review-w4-w5.md`, плюс строка дерева:

```text
Вердикт: принять | принять с замечаниями | вернуть
Предмет: код | план | документ
| # | серьёзность | файл:строка | что не так | сценарий | как проверить | предложение |
Проверено и чисто: <что и какой командой>
Не удалось проверить: <что, почему, какой командой проверить>
Дерево: <вывод python3 scripts/agent_state.py tree . в начале прохода>
```

- Вердикт «вернуть», если открыто хоть одно высокое замечание; «принять с замечаниями» только со
  средними и низкими. Хук `review_stamp.py` ведёт `.review-stamp`: «принять» или «принять с
  замечаниями» по коду пишет для дерева из отчёта, если код с него не менялся; «вернуть», отчёт по
  коду без предмета или дерева, с двумя вердиктами или испорченной строкой отзывают отметку
  (`return` для текущего дерева); отчёт по плану или документу и текст без строки вердикта её не
  трогают. По этой отметке гейт пускает коммит (раздел 5).
- Высокая: исправить до коммита. Средняя: исправить или записать в раздел 7 спеки с причиной.
  Низкая: на усмотрение оркестратора, с записью.
- Спор с ревьюером решает воспроизводимая команда или тест, а не довод.
- Цикл исправлений: оркестратор разбирает каждое замечание (принять или отклонить воспроизводимой
  командой), исправления пишет `implementer` по брифу с номерами замечаний (правку до ~20 строк в
  одном файле оркестратор делает сам), затем `make check` и тот же `reviewer` (SendMessage, контекст
  сохранён) только по изменённым строкам, с новыми строками «Предмет» и «Дерево». Не больше двух
  кругов исправлений: если после второго круга вердикт снова «вернуть», стоп и вопрос владельцу
  (раздел 7).

## 5. Проверки и коммит

- `make verify-fast` в начале сессии и после каждого живого шага: отметка от 23.10 доказывает
  только то дерево и тот стек.
- Полный `make verify` запускает merge silver. По `AGENTS.md` он требует «ок», если в bronze есть
  снапшоты, которых silver не видел. Без отдельного «ок» (класс A) только при трёх условиях: принят
  W6-D4; реплей не играет; последний успешный запуск `silver_upsert` начался позже последнего
  коммита bronze (`select max(committed_at) from lake.bronze."cdc_events$snapshots"` против
  `airflow dags list-runs silver_upsert --state success`). Иначе класс C. Цикл:

  ```bash
  COMPOSE="docker compose --env-file .env -f docker/compose.yaml"
  af() { $COMPOSE exec -T airflow-scheduler airflow "$@"; }
  for d in silver_upsert dbt_build dq_checks; do af dags pause "$d"; done
  for d in silver_upsert dbt_build dq_checks iceberg_maintenance; do af dags list-runs "$d" --state running; done  # пусто у всех
  $COMPOSE stop airflow-scheduler
  make verify                          # последняя строка: verify ok
  $COMPOSE start airflow-scheduler
  # коммит здесь; затем
  for d in silver_upsert dbt_build dq_checks; do af dags unpause "$d"; done
  ```

  `iceberg_maintenance` и `iceberg_orphans` остаются в том состоянии, в каком были.
- Коммит: одна карточка или её логическая часть, один verify, один коммит (ревью п. 23: гейт сверяет
  рабочее дерево, а не индекс, поэтому серия частичных коммитов от одного verify запрещена правилом).
  Порядок: правка; `make check` и затронутые `test-spark`, `dags-check`, `alerts-test`, `dbt-parse`;
  ревью; исправления, снова `make check` и ревью по изменённым строкам; цикл verify; коммит.
  Сообщение `<область>: <что сделано>`, без строк атрибуции. «Итог» карточки и HANDOFF идут
  следующим коммитом `docs:` (только Markdown после полного verify хук пропускает без нового verify).
- Гейт `guard.py` на `git commit`: всегда полный verify этого дерева; при изменённом коде ещё
  `.check-stamp` от `make check` и `.review-stamp` с вердиктом «принять» или «принять с
  замечаниями». Отметка покрывает дерево, если с неё менялись только Markdown и `docs/`; любая
  правка кода после отметки требует нового `make check` и прохода `reviewer`. Отметки пишут только
  `make verify`, `make check` (lint и test на дереве, которое за это время не менялось, без
  переменных make и pytest) и хук. Хук запрещает запись, которую видно по тексту команды: файловые
  инструменты на отметке, команды с её именем кроме чтения, прямой вызов `agent_state.py stamp` и
  `check`, встроенный Python с `agent_state`, `make check` с флагами или переменными. Обход через
  скрипт запрещён разделом 2.1.
- Docker недоступен: код закоммитить нельзя (хук требует полный verify дерева). Незакоммиченным
  держать код не больше одной карточки; дальше только Markdown и `docs/`, их коммитить можно, если
  код в дереве не менялся после последнего полного verify. Код, закоммиченный кем угодно после
  этого verify (в том числе правка хука владельцем), снова требует полного verify перед любым
  коммитом агента. В отчёт: «не проверено», команда, список незакоммиченных файлов.

## 6. Доказательства

Закрытый пункт записывается в «Итог» карточки и в HANDOFF так:

```text
Критерий: <цитата «Готово, когда», файл:строка>
Изменение: <коммит и файлы> | без изменений: <почему>
Проверка: <команда> -> <последние строки вывода>, <дата UTC>, HEAD <hash>
Независимо: <вердикт reviewer или повтор оркестратором>
Не проверено: <что> (<команда>)
Риски: <что осталось>
```

Числа «до и после» снимаются одной и той же командой. Утверждение без команды и вывода в отчёт не
идёт. Документ (README, ARCHITECTURE) описывает только проверенное, план помечается `planned`.

Стоп, отчёт и вопрос владельцу, если:
- нужно действие C или решение из таблицы спеки;
- первичные документы (спека, ADR, код) расходятся так, что меняется поведение;
- `reconcile` или `verify` красный вне сценария отказа, который сам же запущен;
- живое число вне допуска карточки; `OOMKilled` или сумма `docker stats` больше 10 GiB (W4-D5);
- задача превысила оценку вдвое: записать вариант «упростить или вырезать»;
- одна и та же ошибка второй раз: сначала тест, хук или проверка, которые её пропустили (`AGENTS.md`);
- после второго круга исправлений ревью снова «вернуть» (раздел 4).

Не стоп: имена, тесты, локальный рефакторинг внутри карточки, выбор между равноценными обратимыми
вариантами. Такие решения оркестратор принимает сам и пишет одной строкой в отчёт.

## 8. Сессия

1. Старт, только чтение: `make report`, `docker ps`, `gh run list --limit 5`, `make verify-fast`,
   `curl -s 127.0.0.1:9090/api/v1/alerts`, `make replay-status`. Расхождение с HANDOFF записать.
2. Одним сообщением владельцу: решения группы C без статуса «принято» (вопрос, рекомендуемый ответ,
   цена отказа), нужные «ок», обновлённая таблица «Действия владельца» в HANDOFF.
3. Работа по разделу 5 спеки: первая строка с выполненными зависимостями и принятыми решениями.
   Пока решений нет, только работа из строки «без решений» раздела 5 спеки; кончилась: стоп.
4. Цикл карточки (`/task <ID>`): «Вход» (`Explore`, `scout`) → короткий план в отчёт → тест на
   отказ и правка (`implementer`) → `make check` → ревью → исправления (`implementer`, не больше
   двух кругов) → verify → коммит → «Итог» карточки и HANDOFF.
5. Конец: раздел HANDOFF «Состояние на <дата>», `docs/NEXT_SESSION.md`, журнал «ок»,
   `git status --short`, `git diff --stat`, список того, что ждёт владельца.
