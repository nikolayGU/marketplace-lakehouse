silver 7 из 7, инкрементальная витрина равна пересчёту с нуля (EXCEPT в обе стороны 0), GMV

агентский контур, сверки, которые обещают больше, чем проверяют, и документация, которую новая
сессия обязана читать целиком.

Главные выводы:

1. REL-01: мониторинг выключен прямо сейчас и уже второй раз (27.10 и 30.10). Prometheus не
   поднимается после рестарта Docker; сильная гипотеза: процедура перезагрузки правил из
   `OPERATIONS.md:555,580` (`docker kill -s HUP`) ставит контейнеру флаг ручной остановки, и
   `unless-stopped` его больше не поднимает. Никто это не видит (REL-02).
2. SEC-01: агент читает секреты (`.env`, `docker compose config`, `docker inspect`); deny есть
   только на `Edit(.env)`.
3. SEC-04: guard сверяет текст команды; запись скрипта, `python3 -c` со склейкой слов и запись
   отметки ревью обходят его. Это защита от ошибок, а не граница; `make down` (SEC-03) проходит
   без окна вовсе.
4. DATA-01: `make verify` обещает «silver equals Postgres», а для `orders` сверяет только число
   строк и набор ключей; значения сверяет только `dq_checks`.
5. DATA-02: сверка silver-gold в `dq_checks` может не выполняться часами без сигнала.
6. REL-03: у задач Airflow нет таймаутов, а наивный таймаут с текущим `DockerOperator` может
   запустить второго писателя checkpoint silver.
7. REL-04, REL-05: копия warehouse 29.10 без каталога, checkpoint и ключа шифрования
   Lakekeeper; восстановление ни разу не проверялось; RPO и RTO не определены.
8. SEC-02: пустой `BIND_IP` публикует все порты на все интерфейсы, а вся защита сервисов без
   аутентификации держится на loopback.
9. DOC-01..04: обязательное чтение на старте около 420 КБ (оценка 120k токенов), из них 66 КБ
   истории HANDOFF; правила агентов противоречат друг другу (push, упоминания AI, порядок
   чтения); закрытые планы без статуса.

Находки: P0 0, P1 0, P2 21, P3 44 (раздел 3). Что исправлено в этой сессии и что ждёт
владельца: раздел 9.

Оценка. Воспроизводимость: высокая (путь с чистого клона доказан smoke 29.10, одна
последовательность `make secrets`, `make bootstrap`). Безопасность: адекватна локальной
лаборатории на loopback, с явными ограничениями (без аутентификации, сокет Docker); не годится
для любой сети без доработки. Устойчивость: восстановление после типовых отказов доказано
chaos-сценариями 1-9; восстановление после потери тома или `.env` не доказано, и сбой
мониторинга сейчас не обнаруживается.

## 4. Безопасность

Границы доверия: хост и контейнеры (порты только на `${BIND_IP}`, сейчас 17 из 17 на
127.0.0.1); сеть `lake` без аутентификации у Trino, Connect, Lakekeeper, Kafka, Airflow
(`SIMPLE_AUTH_MANAGER_ALL_ADMINS=True`); сокет Docker (scheduler на запись, exporter `:ro`, но
`:ro` не ограничивает API, ограничивает код: только GET, `client.py:27-31`); публичный GitHub и
CI (`pull_request`, не `pull_request_target`; `permissions: contents: read`; `${{ github.event }}`
в `run` нет); агент и репозиторий (хуки по тексту команды).

Пути атаки: (1) процесс или страница в браузере на хосте бьёт в 127.0.0.1 сервисы без
аутентификации (малый риск лаборатории); (2) UI Airflow, затем сокет Docker, затем root на хосте
(ADR-011); (3) недоверенный текст попадает в контекст агента, затем команда, которую guard не
распознаёт, или вывод секретов (SEC-01, SEC-04, AI-01); (4) подмена тега action или образа
(SEC-09); (5) персональные данные в публичной истории (SEC-11).

Секреты: в HEAD нет (11 срабатываний gitleaks только в неотслеживаемом `.env`, mode 600, в
`.gitignore`); в истории всех ссылок нет; секретов с неизвестной действительностью нет; ротация
не нужна. Значения по умолчанию лаборатории: `change_me` в `.env.example` (SEC-10).
`scripts/make_env.py` генерирует 192-битные секреты и ключ Fernet, `chmod 600`, не перезаписывает.
